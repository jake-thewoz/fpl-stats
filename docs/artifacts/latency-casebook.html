The 128 MB bottleneck

Why the app took 2–10 seconds to show anything, how we found the cause in a couple of commands, and what one CDK line changed. The second half covers the AWS options still open in the latency milestone.

Part one

How we tracked it down

The method is to split the request into pieces and time each piece on its own, so you only work on the piece that's actually slow. Each step below rules out one suspect.

Time the request from outside

curl -w reports when each phase of a request finished. Comparing a trivial endpoint with a real one tells you whether the network or the server is to blame. /health runs a Lambda that does nothing, so it shows the fixed cost of DNS, TLS, API Gateway and Lambda invocation.

$ curl -s -o /dev/null -w "ttfb=%{time_starttransfer}\n" "$API/health" ttfb=0.075 $ curl -s -o /dev/null -w "ttfb=%{time_starttransfer}\n" "$API/gameweek/current" ttfb=2.497 # warm, 2.7 KB response
Time to first byte, warm, measured 10 October 2026 before the fix
Network + API Gateway + invoke Inside the Lambda handler

Network and API Gateway account for about 70 ms. Everything else happens inside our code.

Read Lambda's own report

Every invocation writes one REPORT line to CloudWatch Logs. It's the cheapest profiler AWS gives you, and nothing needs to be installed to get it. Tap a field to see what it means.

REPORT RequestId: 3f1c…a9

Tap a field above.

The REPORT line explains the curl result: the handler itself took 2.45 s, at 105 of 128 MB. A function using 82% of a small memory allowance and still taking seconds is the signature of a CPU-starved Lambda.

Run the same work somewhere with a full CPU

To check whether the work itself is heavy, we ran the handler's steps from a laptop against the real table: get_item on the ~500 KB bootstrap item, deserialising it, validating it with pydantic, and querying the 667 xP rows.

bootstrap get_item 0.147 s # includes the WAN round trip to us-east-1 TypeDeserializer 0.006 s pydantic validate 0.003 s xP query, 667 rows 0.178 s

About 0.35 s in total, mostly network. The work is small, so the Lambda environment itself must be the problem.

Connect it to how Lambda allocates CPU

Lambda has no CPU setting. You choose memory, and AWS gives CPU in proportion to it: 1,769 MB buys one full vCPU, so 128 MB is about 7% of one. Our handlers spend most of their time parsing JSON and building Python objects, which is CPU-bound, so they ran roughly 14× slower than they needed to. We had hit the same wall before, when the xP analyzer timed out at 256 MB.

Part two

The fix: one line of CDK

PR #183 changed the default in backend/lib/fpl-python-function.ts from 128 to 1024 MB, so every read Lambda got eight times the CPU share. A jest test now fails if any Read API function drops below the default.

// Lambda CPU scales linearly with memory. At 128 MB the read handlers // took 2–5 s warm for ~0.3 s of real work (#176). - memorySize: 128, + memorySize: DEFAULT_MEMORY_MB, // 1024

The cost stayed flat

Lambda bills memory × duration, in GB-seconds. Eight times the memory for an eighth of the time is the same bill: 0.125 GB × 2.43 s ≈ 1 GB × 0.31 s ≈ 0.30 GB-s. For CPU-bound work, more memory is nearly free.

Init barely moved

Cold-start init stayed at 0.6–1.2 s. Init is mostly loading the runtime and importing boto3 and pydantic, and extra memory did little for it. More memory can't get rid of cold starts; caching in front of Lambda can (see #179 below).

Memory used is a poor guide

Max Memory Used is now ~120 of 1024 MB. That looks like over-provisioning, but the memory is there to buy CPU. Size Lambdas by duration, not by memory used.

Taking Lambda off the hot path

How it works

Watch out for

Small tweak

Reuse work across warm invocations

Code at module level runs once per execution environment and stays alive between invocations. Parsing the bootstrap into a global, keyed by its fetched_at, would skip the 500 KB parse on most warm calls.

Small tweak

ARM64 (Graviton)

architecture: Architecture.ARM_64 in CDK. About 20% cheaper per GB-second and often a little faster. Docker bundling then has to build ARM wheels, which matters for pydantic-core.

Remaining hot spots

xP and Transfers

xP is still 0.7 s warm: a paginated 667-row query, each row turned into Decimals. Transfers was already at 1024 MB and still takes about 8 s, because that's real computation. Precomputing (#181) or speeding up the algorithm are the levers there.

Considered and rejected

Rejected

Provisioned concurrency

Keeps environments initialised so there are no cold starts, but you pay for every hour they sit ready, and there's no free tier. CloudFront removes most cold starts for free.

Rejected

SnapStart for Python

Restores a snapshot of an initialised environment instead of running init. It works, but caching and restoring snapshots are both billed.

Rejected

Keep-warm pings

An EventBridge rule invoking each function every few minutes. It warms only one environment per function, so two users at once still hit a cold start. It hides the problem rather than fixing it.
