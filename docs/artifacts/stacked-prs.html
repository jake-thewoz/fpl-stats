Stacked PRs, step by step

A replay of what happened to fpl-stats #173 and #174: why the second PR never reached main, how it should have gone, and how #175 brings it home. Each dot is a real commit from the repo.

A branch is a label

It points at one commit. A new commit on the branch moves the label forward. Nothing else does.

A PR has a fixed target

"Merge head into base." The base stays what you picked until someone changes it.

Merging moves one label

Merging a PR adds a commit to its base branch and moves only that label. Other branches don't notice.

Checking it yourself

    

      
gh pr view 174 --json state,baseRefName --jq '.state + " into " + .baseRefName'

      
Prints what a PR merges into. Before merging the child of a stack, this should say main. For #174 it said MERGED into fix/plan-for-next-deadline.

    

    

      
git fetch && git log --oneline -5 origin/main

      
After any merge, the PR's commits should show up here. If they don't, the PR landed somewhere else.

    

    

      
gh api -X PATCH repos/jake-thewoz/fpl-stats/pulls/174 -f base=main

      
Retargets an open PR. Use this instead of gh pr edit --base, which fails in this repo with a "Projects (classic) is being deprecated" error.

    

    

      The easy way out: let GitHub do it
      
Turn on Settings → General → Automatically delete head branches. When #173 merges, GitHub deletes fix/plan-for-next-deadline, and any open PR based on it, like #174, is retargeted to main for you. That retarget is the step that went missing here.
